# Production label

`expensive-label.zpl` is the clean final format from `label/L3 expensive.prn`. It retains the original Z64 warning graphic, ATTENTION/Very Expensive captions, 354 × 591 dot geometry, orientation and fonts. Its PN text, native Code 128 PN barcode and MPN use three unique placeholders populated from the same selected component as the normal label. Its original setup/cancel/save preamble is excluded, and its encoding is unified with the normal template. For expensive items, `LabelJobRenderer` concatenates the normal format and this warning format, each with one-copy `^PQ1,0,1,Y`, into a single RAW submission. The application's EXPENSIVE ITEM💰 display suffix is not added to either label's identifiers. The separate `ValidatedExpensiveTemplateSha256` must record physical validation before an expensive production job is allowed.

The operator can mark the reception date **Not available**. This explicitly encodes **0000** in both the date text and native Code 128 date barcode, using the same template fields. It does not change the stored month/year or the label geometry.

`production-label.zpl` preserves the positions, rotation, fonts, barcode height and one-sticker quantity from the final format block in `label/L3.prn`. Although the implementation brief calls that export `L3(2).prn`, the repository's `L3.prn` contains the same two native `^BC` barcodes and field layout. The original `.prn` and `.nlbl` files are untouched.

The template deliberately omits the original setup preamble, malformed BOM/control-byte prefix, `~JA` cancellation, and `^JUS` configuration save. The renderer supplies only the six unique named fields. `Date:` and `Qty:` remain fixed captions; `^PQ1,0,1,Y` always requests one sticker. Quantity is a component count, never a spooler copy count.

All variable data is encoded as UTF-8 bytes and every byte is represented using `^FH\` hexadecimal field escapes. `^CI28` is set once for the complete format. This deliberately replaces the export's mixed `^CI27`/`^CI28` handling. An MPN containing `^`, `~`, a backslash or placeholder-like text cannot insert a ZPL command. Dry runs preserve Unicode, but the supplied `Q` MPN font does not establish Unicode glyph support. Production therefore accepts printable ASCII MPNs without backslashes; supporting other glyphs requires a font/template change and hardware validation. Confirm the actual printer has the required `Q` font mapping.

OEPS PN text accepts exactly `OEPS`, an optional following hyphen, and at least three ASCII alphanumeric suffix characters. It formats `OEPS-AB1234` as `OEPS AB 1234`. Barcode data remains the database identifier, including its hyphen and letter case. Unsupported identifiers are reported instead of silently rewritten. Reception years are 2000–2099, avoiding ambiguous centuries in the printed `MMYY` format.

The Code 128 encoder minimizes the number of B/C symbols using explicit start/latch invocation sequences. The barcode command is explicitly `^BCB,56,N,N,N,N`: original backward rotation and 56-dot height, no interpretation line, no UCC transformation, normal mode. Dates use Code C. Data values cannot introduce invocation controls because the barcode alphabet is restricted to ASCII letters, digits and hyphens. The printer supplies the normal Code 128 checksum.

The barcode geometry check reserves a 10-module quiet zone at each end. At the preserved 3-dot module width, each quiet zone is 30 dots. A backward barcode extends from its `^FT` Y coordinate toward decreasing Y, so the bounds are `bar width + 30 <= anchor Y` and `anchor Y + 30 <= 591`. The PN anchor is 487 and the date anchor is 228; total bounds including both quiet zones are therefore 517 and 258 dots. For example `OEPS-AB1234` needs 495 dots, and a four-digit date needs 231 dots. These calculations are a layout precheck, not proof of physical fit or scan quality. Font 0 is proportional, so equal character counts do not guarantee equal text widths. Production also uses conservative limits of 34 MPN characters and 7 quantity digits for the unchanged text fields.

The renderer intentionally accepts only the supplied layout (line-ending differences are allowed), because fit calculations depend on these positions, widths and fonts. A revised design requires corresponding renderer changes and new physical validation; changing the JSON hash alone cannot enable arbitrary ZPL. `TemplateSha256` is the SHA-256 of the original template file text encoded as UTF-8 without a BOM, including its line endings and trailing newline. For the supplied BOM-free file, obtain it with:

```powershell
(Get-FileHash -Algorithm SHA256 -LiteralPath .\templates\production-label.zpl).Hash.ToLowerInvariant()
```

Before enabling production, confirm the actual Zebra model, printhead DPI, connection, exact Windows queue, media and ribbon. Check the Zebra software edition if the original design needs editing. The layout is **354 × 591 dots**; no physical millimetre dimensions are assumed. Configure `Model`, `Dpi`, `Connection`, `QueueName`, `MediaTracking` (`continuous`, `web`, or `mark`), `PrintMethod` (`direct-thermal` or `thermal-transfer`), `PrintSpeedIps`, and `Darkness`. The renderer sends explicit per-job media, print method, speed and darkness commands; it resets relative darkness to zero, units to dots, origin to zero and normal orientation/mirroring. Only choose values supported by the actual model.

Use dry-run ZPL to inspect every mapped field. On the actual device, validate the template with the longest and widest supported PN (including wide letters), its barcode quiet zones, both barcode scans, the longest MPN, all date values, maximum intended quantity, text fit and legibility, DPI and media/ribbon settings. Have an operator deliberately submit the inspected dry-run job using the printer's normal validation tool; dry-run itself never accesses a printer. Record the exact template hash in `ValidatedTemplateSha256`, the validated longest/widest identifier in `LongestValidatedOepsPn`, and the validation observations in `ValidationNotes`. Only then set `ProductionValidated` to true and turn off dry run. A different selected queue, changed hash, or PN exceeding the validated barcode/text length blocks production.

The Windows transport creates one RAW spooler job and checks every native result. Successful short writes continue with only the unsent bytes. Errors abort the document best-effort, close handles, and clearly identify uncertain submissions. The app never automatically retries; inspect the queue and printer before an operator decides to click again. “Sent to printer” means spooler submission completed, not that a physical sticker was observed.
